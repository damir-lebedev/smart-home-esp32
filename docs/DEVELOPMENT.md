# Разработка

Этот документ — для тех, кто будет читать и дорабатывать код, а не для конечного пользователя. Если нужно просто прошить и настроить модуль — см. [README.md](../README.md).

## Общая идея

Все модули в сети — slave или master — это **одна и та же прошивка**. Роль (`master`/`slave`) и тип (`relay`/`rgb`) — это не разные билды, а рантайм-настройки в NVS (`Preferences`), заданные через `/config`. Отличие ролей только в одном: master дополнительно регистрирует `/fleet/*` (см. `ota.cpp`, гейт `if (role == "master")`) — всё остальное, включая полный дашборд со всеми комнатами, работает одинаково на любом модуле.

Это значит: любой узел можно временно превратить в master (через `/config`), чтобы раскатить прошивку на остальных, а потом вернуть обратно в slave. Именно так в этом проекте раскатывались обновления, когда физический «мастер» был недоступен — см. раздел про self-OTA ниже.

## Карта файлов

- `src/main.cpp` — `setup()`/`loop()`, порядок инициализации (см. комментарии в файле — там же объяснено, почему `relayForceOff()` обязан идти после `relayLoadConfig()`, и почему `Serial.begin()` вызывается так поздно)
- `src/globals.*` — общее состояние: WiFi/сервер/сокет, реле- и RGB-state, `role`/`moduleType`/`deviceName`, `discoveredModules`, OTA-ключ
- `src/net_setup.*` — точка доступа для первичной настройки (`/`, `POST /save`) и `/config` для последующей смены имени/роли/типа/полярности/пина/ключа
- `src/relay.*` — реле: `/on`, `/off`, `/toggle`, поддержка инвертированной полярности
- `src/rgb.*` — RGB-лента: режимы, цвет, яркость (с хардкапом), скорость, настраиваемый пин данных
- `src/discovery.*` — обнаружение модулей по UDP-broadcast
- `src/ws_events.*` — WebSocket-push при смене состояния (для мгновенного обновления дашборда без polling)
- `src/web_ui.*` — HTTP API и единый дашборд (`/status`, `/ui`, `/modules`, `/master`, `/`)
- `src/ota.*` — self-OTA (ElegantOTA-портал на каждом модуле) и master-only рассылка прошивки по сети
- `src/health.*` — watchdog и автопереподключение/автоперезагрузка при потере Wi-Fi

## Discovery: как любой узел видит весь дом

Раньше список модулей строил только master (см. git-историю `discovery.cpp`) — из-за этого страница любого slave показывала только саму себя. Сейчас протокол устроен проще и симметричнее:

Каждый модуль раз в `ANNOUNCE_INTERVAL` рассылает по UDP-broadcast (порт `UDP_PORT`) JSON:
```json
{"cmd":"announce","role":"slave","name":"Спальня","type":"relay","ip":"192.168.10.34"}
```
**Любой** модуль, получивший такой пакет, кладёт отправителя в свою собственную `discoveredModules` — независимо от собственной роли. Дополнительно, если у отправителя `role:"master"`, получатель запоминает его как «текущий известный мастер» (`discoveryGetMaster()`) — это используется только для необязательной ссылки «🏠 Мастер (имя)» в футере дашборда.

Отсюда следствие: если на модуле по ошибке стоит `role: master`, он не перестаёт быть виден остальным (он всё равно шлёт `announce`), но сам он не покажет в своём `/modules` то, чего не должно быть — только то, что реально услышал по UDP.

## Единый дашборд и его квирки

`webUiRegisterDashboardRoute()` регистрирует «/» одинаково на любом модуле. Разница в поведении — чисто на JS-стороне, через переменные `MY_ROLE`/`OWN_IP`, подставленные сервером в HTML при рендере:
- футер с «Настройки, прошивка» (панель OTA-заливки) появляется только если `MY_ROLE === "master"` — вызывать `/fleet/upload`/`/fleet/deploy` со slave всё равно бессмысленно, они там не зарегистрированы (401/404).
- ссылка «🏠 Мастер (имя)» — наоборот, полезна только если ты НЕ мастер.

Каждая плашка модуля на дашборде подгружается через **кросс-девайсный fetch**: `loadModuleCard()` в JS делает `fetch('http://<ip другого модуля>/ui')`, вставляет фрагмент через `innerHTML`, дальше опрашивает `/status` этого же IP напрямую из браузера. Это работает без CORS-проблем только благодаря `DefaultHeaders::Instance().addHeader("Access-Control-Allow-Origin", "*")` в `main.cpp` — без него браузер не дал бы JS прочитать ответ с чужого IP (сам запрос всё равно бы ушёл и отработал, но ответ был бы недоступен для чтения).

**Не оборачивайте фрагменты `/ui` в свой собственный `.module-card`** — обёртку уже создаёт `loadModuleCard()` на JS-стороне. Раньше это было не так, из-за чего рамка и тень дублировались (одна карточка внутри другой) — если увидите двойную рамку на плашке, это тот самый баг вернулся.

## RGB: пин — не просто переменная

`FastLED.addLeds<WS2812, PIN, GRB>(...)` требует пин как **compile-time шаблонный параметр** — нельзя просто передать туда `uint8_t` из prefs. Поэтому настраиваемый пин ленты (`ledpin` в `/config`, для модулей с разной распайкой) реализован через `switch` по конкретным пинам в `addLedsOnPin()` (`rgb.cpp`). Если понадобится поддержать пин за пределами диапазона 0–10 — добавьте `case` туда же, а не пытайтесь сделать это динамическим — так FastLED не умеет.

Яркость жёстко ограничена в прошивке (`RGB_MAX_BRIGHTNESS = 216`, то есть 85% от 255) — это сознательное ограничение для защиты диодов от перегрева/выгорания на полной яркости, а не баг. Ограничение применяется и при загрузке из prefs, и при каждом `/brightness?val=`, так что обойти его через прямой HTTP-запрos нельзя — единственный способ поднять потолок — поменять константу в коде.

## OTA-раскатка по сети: как это устроено и на чём подвисает

Загруженная через `/fleet/upload` прошивка **не хранится на файловой системе** — она пишется напрямую в неактивный OTA-раздел через `esp_ota_begin/write/end` (см. `ota.cpp`) и раздаётся остальным модулям чтением из того же раздела (`/firmware.bin`). Так экономится место на 4MB флеше, где и так заняты два полноразмерных app-раздела под OTA (`partitions.csv`) плюс раздел под coredump.

`masterDeployTick()` — это последовательный конечный автомат: на каждой цели он запоминает её текущую версию прошивки, дёргает `/fleet/pull` (или планируетself-update, если цель — это сам master), а затем поллит `/status` этой цели, пока версия не изменится (или пока не истечёт `OTA_STEP_TIMEOUT` = 90с). **Именно поэтому `FIRMWARE_VERSION` в `globals.h` обязательно бампать перед каждой сборкой** — если версия не поменяется, автомат не сможет отличить «обновился» от «завис», и после 90с спишет цель в таймаут, даже если она на самом деле всё сделала правильно.

### Известная проблема: self-target OTA ненадёжен

Если master пытается обновить **сам себя** (`includeSelf=1`), он одновременно должен быть HTTP-клиентом (внутри блокирующего `httpUpdate.update()`) и HTTP-сервером, отвечающим на тот же самый запрос к `/firmware.bin`. На практике это наблюдалось так: устройство просто зависает на старой версии без явной ошибки, а деплой в итоге списывает его в «таймаут».

Рабочий обход, проверенный в бою: **флешить устройство не через самого себя, а через другой узел**, временно назначенный master:
1. `POST /config` на узле-помощнике с `role=master` (сохранив остальные его настройки как есть).
2. `POST /fleet/upload` + `POST /fleet/deploy?includeSelf=0` (или `1`, если помощник тоже должен обновиться) — деплой заденет всех, кого этот узел видит в своей `discoveredModules`, включая нужную вам цель.
3. После завершения — вернуть узлу-помощнику `role=slave` обратно через `/config`.

## Другие грабли, на которые уже наступали

- **Одна неудачная попытка подключения к Wi-Fi стирает вообще все настройки модуля.** В `main.cpp`: если `netConnectSTA()` не смог законнектиться за 14 секунд — `prefs.clear() + ESP.restart()`, без разбора причины. Это осознанный компромисс (иначе не выбраться из цикла с неверным паролем), но у модуля в зоне слабого сигнала это может сработать на ровном месте после банальной перезагрузки роутера — тогда он поднимется в режиме точки доступа и попросит настроить себя с нуля.
- **Многобайтные имена (эмодзи, кириллица) в именах модулей легко бьются при скриптовой отправке `POST /config`.** Если шлёте форму не из браузера, а из shell/скрипта — не подставляйте юникод-строку напрямую в командную строку, кодировка терминала может её испортить ещё до того, как curl увидит байты. Надёжнее: записать имя в файл и передать `--data-urlencode "name@файл"` — так курл возьмёт байты из файла как есть.
- **Не путайте физическое устройство с его именем в интерфейсе.** В этом проекте уже пытались перевести обычное реле в тип RGB, ориентируясь на название «Подсветка» — а физически это оказалась прихожая с обычным реле. Тип модуля — это факт о железе (реле или адресная лента), а не про то, как его назвали.

## Как добавить новый тип модуля

Возьмите `relay.*` или `rgb.*` как шаблон:
1. Заголовочный файл с `<type>Init()` (если нужна ранняя инициализация железа), `<type>LoadConfig()`, `<type>RegisterRoutes()`, и, если есть анимация/поведение во времени, `<type>Loop()`.
2. Ветки по `moduleType` в `main.cpp` (`setup()` и, если нужен `Loop()`, в `loop()`).
3. Поле состояния в `globals.h`/`globals.cpp`, отдаваемое через `/status` (`web_ui.cpp`, `webUiRegisterCommonRoutes()`).
4. UI-фрагмент — новая функция вроде `getRelayUiFragment()`/`getRgbUiFragment()` в `web_ui.cpp`, подключаемая в `/ui`.
5. Если нужны настраиваемые под конкретное железо параметры (пин, полярность и т.п.) — добавьте поле в форму `/config` (`net_setup.cpp`, и `renderConfigPage()`, и `handleConfigSave()`) по образцу `invert`/`ledpin`.

## Сборка, прошивка, отладка

```
pio run                                   # собрать
pio run -t upload --upload-port COMx      # прошить конкретный модуль по USB
pio device list                           # найти, на каком COM-порту какой модуль
```

Serial-лог у модулей на нативном USB (без отдельного USB-UART моста) не покажет вообще ничего, пока модуль не пройдёт `Serial.begin()` в `main.cpp` — а это происходит только **после** успешного подключения к Wi-Fi. Тишина в порту не значит, что модуль завис — он может быть жив и просто ещё не достучался до роутера (или уже ушёл в цикл сброса настроек, см. грабли выше).
